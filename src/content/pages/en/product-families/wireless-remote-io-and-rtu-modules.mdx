# Wireless Remote I/O and RTU Modules

Remote I/O and RTU-class products matter when the site needs more than a network connection. A router can connect a site. A gateway can move data. Remote I/O and RTU-class devices interact with field signals, alarms, counters, basic control behavior, and local states when the network is weak or unavailable.

The category gets confusing because product names overlap. Some devices call themselves gateways while providing I/O. Some RTUs include cellular. Some remote I/O modules support simple logic. The useful way to evaluate the class is by responsibility, not label.

## Quick answer

Use wireless remote I/O when the job is modest field signal collection with simple reporting. Use an RTU-class device when the site needs local alarm logic, basic control, store-and-forward behavior, or survivability during communications loss. Use a telemetry gateway or router when the field logic already exists elsewhere and the primary problem is backhaul, protocol movement, or remote access.

For searchers using the phrase **wireless I/O**, the practical question is usually narrower: "Can I collect field points without building a full control cabinet or SCADA remote terminal?" Sometimes yes. But if the site has alarms, outputs, or outage consequences, the answer quickly moves from wireless I/O toward RTU-class behavior.

## Device-class boundary

| Device class | Best fit | Weak fit |
| --- | --- | --- |
| Wireless remote I/O | A small number of discrete or analog points, modest local behavior, simple installation | Complex local logic or multi-protocol aggregation |
| RTU-class module | Alarm handling, local state, simple control, store-and-forward, harsh unattended sites | Pure networking or high-throughput edge compute |
| Telemetry gateway | Protocol translation, data buffering, upstream delivery, several connected devices | Direct field wiring without enough local I/O support |
| Industrial router | Cellular or Ethernet backhaul, VPN, remote access, failover | Field-side signal ownership or local alarm logic |

## The selection criteria, in decision order

This is the canonical criteria set for the category — the same nine criteria the product database index summarises. Each criterion is stated without model numbers on purpose: the numbers belong to individual records in the live table below, where every figure carries its manufacturer source.

| Criterion | What to decide | Why it decides the shortlist |
|---|---|---|
| I/O types and count | Which of DI / DO / AI / AO the point needs, and how many of each | The module is bought per point; a mismatch here cannot be fixed by any radio feature |
| Update rate and latency | How fresh the values must be, and whether outputs are control or monitoring | Update rate drives battery life, gateway capacity and band occupancy more than any other choice |
| Network form | Point-to-point signal mirroring, or a networked module reporting to a gateway or host | Mirrored pairs replace one cable run; networked modules scale to plants — different products, different failure modes |
| Band and licensing | Licensed or licence-free band, and the regional rules where the device will be installed | The same model is often a different radio in the EU and the US; a band the site survey cannot support is a non-starter |
| Range and site survey | Real path conditions — obstructions, antenna height, interference — against the manufacturer's condition-bound range figure | Range is only meaningful with its stated conditions; unsourced "up to" figures are not comparable between makers |
| Power source | Battery, solar, loop power or wired supply at the mounting point | Power decides the maintenance model of the whole installation and caps the update rate |
| Fail-safe behaviour | What outputs must do when the link drops — hold last value, drive to a safe state, or time out | This is a safety property of the loop, not a feature checkbox; it must be specified, not discovered |
| Hazardous area and ingress | The area classification and IP rating the location demands | Certification is per-model and per-variant; it eliminates otherwise suitable products outright |
| Host interface | How values reach the PLC or SCADA system — Modbus, EtherNet/IP, OPC UA, MQTT, a protocol uplink | The best radio is useless if the host cannot read it without a second conversion |

The decision order matters: **count I/O and update rate first, choose the network form second, and compare brands and models last.** Reversing that order — starting from a catalogue — is how projects end up with excellent radios wired to the wrong I/O.

## Wireless I/O versus RTU: the real split

| Requirement | Wireless remote I/O is usually enough | RTU-class behavior is safer |
| --- | --- | --- |
| Read a few tank, pressure, door, or run-status points | Yes | Only if alarm sequence or local control matters |
| Preserve exact alarm order during a network outage | Sometimes | Usually |
| Control a relay output based on local condition | Sometimes | Usually |
| Run on solar or limited backup power | Often | Often, but logic and reporting must be tuned |
| Replace device by field technician with minimal software | Often | Depends on configuration discipline |
| Support several protocols and upstream consumers | Usually not | Sometimes, or use a gateway |

The product label is less important than local responsibility. If the device must decide, latch, buffer, or protect state locally, treat it as more than remote I/O.

## What to define before selection

1. **Signal count and type**: discrete inputs, analog inputs, pulse counters, serial devices, relay outputs, or mixed points.
2. **Local decision requirement**: whether the site must latch alarms, stop equipment, preserve event order, or operate during an outage.
3. **Reporting pattern**: periodic updates, report-by-exception, alarm-first, or bulk store-and-forward.
4. **Power budget**: line-powered cabinet, solar/battery, backup-only, or low-power unattended profile.
5. **Maintenance owner**: utility technician, controls engineer, electrician, integrator, or remote support provider.

If these are undefined, the buyer is comparing boxes before defining the job.

## When remote I/O is enough

Remote I/O can be enough when:

- the signal list is small and stable;
- the site does not need complex local logic;
- communication loss is acceptable for short periods;
- the upstream system owns most interpretation;
- and field replacement should be simple.

This fits many tank level, pump status, valve position, door contact, basic alarm, and environmental monitoring cases.

## When RTU behavior is justified

RTU-class behavior becomes more important when:

- alarm sequence matters during network outages;
- outputs must be controlled locally;
- field conditions change faster than the reporting interval;
- the site must retain last-known state and event history;
- or the site cannot wait for cloud or SCADA availability before taking a local action.

In those cases, the local device is part of the reliability architecture, not just an I/O adapter.

## Before you replace a cable run with wireless I/O

Replacing a cable run is the most common reason this category gets bought, and the checks are different from a new-build selection:

1. **Survey the real path.** Walk the route the signal will take: obstructions, metal structures, seasonal foliage, and other radios on the band. A manufacturer's range figure only counts with its stated conditions — antenna height and line of sight dominate.
2. **State the link-loss behaviour.** A cut cable is obvious; a fading radio is not. Decide per output whether it holds its last value, drives to a safe state, or times out — and how the host learns the link is down.
3. **Match the update pattern to the loop.** A status point that changes twice a day and a control loop that needs a one-second refresh are different products, even at the same I/O count. Report-by-exception behaviour is what makes battery power realistic.
4. **Price the whole change.** The cable disappears, but antennas, surge protection, mounting and a survey appear. The saving is usually in trenching and downtime, not in hardware.
5. **Plan the spare.** A wired run is repaired with cable and connectors; a wireless point is repaired with a configured spare module. Stock the spare and record its configuration.

## How wireless I/O reaches the PLC or SCADA system

The radio link is only the first hop. Values reach the host in one of three patterns:

- **Mirrored pairs** deliver the signal as if the wire still existed — the receiving unit reproduces the inputs as local outputs or register values the PLC already reads.
- **Networked modules** report to a gateway or host over a field protocol — Modbus registers are the most common shape, with WirelessHART, ISA100.11a and IO-Link Wireless networks presenting their values through their gateway.
- **Gateway uplinks** carry the aggregated data onward as Modbus TCP, OPC UA or MQTT. That conversion belongs to the gateway layer, not the module — the layering is covered in [telemetry protocol fit](/protocols/telemetry-protocol-fit/).

If the host cannot consume any of these shapes without a second converter, the module choice is wrong no matter how good the radio is.

## Acceptance checks

Before rollout, test:

- normal signal reads;
- alarm transition capture;
- lost-network behavior;
- local buffer capacity;
- power restart and brownout recovery;
- output fail-state behavior;
- replacement and configuration procedure;
- and what the upstream system displays when the remote device is offline.
